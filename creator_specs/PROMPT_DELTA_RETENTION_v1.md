## What "phần giữa" means for this content format

Every Short generator in this repo produces 4-6 sentence, ~20-30s scripts (verified: every `_GENERATE_CANDIDATES_PROMPT` in all 10 in-scope files specifies "4-6 câu"). There is no separate "beat" structure like Long-form — "phần giữa" here means: **the sentence(s) between the opening hook (sentence 1) and the closing/payoff sentence(s)**. The existing shared retention block (`short_judge_panel_engine.py:40-48`) already has 2 rules — hook must land fast (rule a), ending must echo/land memorably (rule b) — but **nothing governs what happens in between**. This delta adds that missing rule.

**Core principle (redefined per Codex round-1 finding #1/#2, wording tightened per round-3 finding #1 to remove leftover collective-remainder language):** the middle isn't governed by one narrow mechanic ("never answer early"). The general requirement, applied **per sentence, not to the remainder as a block**, is: **every individual middle sentence must itself create progression toward the hook's specific promise** — new information, a new angle, a consequence, a contrast, or a next step — not just restate or decorate what was already said. Answering a hook's question fully and early is **not itself a violation** — but every middle sentence that follows must still, *on its own*, add something. A single wasted middle sentence (pure restatement/decoration, no new content) is enough to fail the check, **even if other middle sentences in the same script do add real value** — later or earlier progression does not retroactively excuse one wasted sentence. Premature-full-resolution (hook poses a specific promise, sentence 2 fully discharges it) is not itself a violation — it only becomes one if a later middle sentence, individually, adds nothing new. This is the single concrete, auditable failure pattern this delta was drafted from — not a restatement of the whole rule.


### A.3 — Why no code-level hard cap (unlike rule (a)'s `HOOK_MAX_FIRST_SENTENCE_WORDS`), matching rule (b)'s existing precedent

Rule (a) has a code-level backstop (`_validate_verdict()`, lines 191-195) because "first sentence word count" is a cheap, reliable, objective proxy with a wide/generous threshold designed specifically to avoid false positives (documented at line 51-55: *"ngưỡng RỘNG RÃI... chỉ bắt câu hook thật sự cồng kềnh... tránh false positive"*). Rule (b) ("does the closing sentence echo the hook or land memorably") has **no** code backstop — it is judged, not measured, because there is no cheap objective proxy for it without a high false-positive rate.

**Rule (c) belongs with (b), not (a):** "did each middle sentence create real progression" is a semantic judgment (compare each sentence's content against what came before *and* against the hook's promise) with no reliable structural proxy. **Confirmed during round-1 revision: no cheap proxy was found that wouldn't produce the false positives/negatives Codex flagged** — sentence count doesn't test whether content repeats; keyword-overlap-between-sentences is easily defeated by paraphrase (exactly what both confirmed violations do — "Tuổi Gà/Trâu/Rắn" restated via different framing each time) and easily triggers false positives on legitimately-repeated proper nouns (e.g. a script correctly saying "Tuổi Dậu" twice while adding new information each time). **No code-level enforcement is proposed for rule (c)** — a deliberate design choice, not an oversight.

### A.4 — Process-level (not code-regex) audit trail — added per Codex round-1 LOW finding

Codex round 1 explicitly did not recommend a weak structural proxy for enforcement, but suggested a lighter observability step instead of no backstop at all. **Minimal-footprint proposal, no new required JSON field, no per-generator schema change:** every generator's existing judge prompt already returns a `"feedback"` string field (confirmed present in all 10 files' `_JUDGE_PROMPT` return-JSON instructions, e.g. `educational_short_generator.py`: `"feedback": "vì sao chọn bản này"`). Add one sentence to `_RETENTION_CHECK_BLOCK` instructing the judge to name, inside that *existing* field, which retention criterion (if any) capped the score:
```
Khi áp dụng trần điểm ở (a)/(b)/(c), hãy nêu rõ trong "feedback" tiêu chí nào đã khiến hook_score bị ép trần -- phục vụ audit thủ công định kỳ (đọc lại feedback qua nhiều lần chạy để ước lượng tần suất rule (c) bị vi phạm), KHÔNG yêu cầu field JSON mới, KHÔNG được code tự động parse/validate nội dung này.
```
This gives a real (if manual) way to later assess rule (c)'s real-world hit rate without pretending a regex can judge semantic progression — directly answering the LOW finding's suggestion without the schema-change cost of a new structured field across 10 files.
